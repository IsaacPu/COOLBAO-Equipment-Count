# 产品案例｜从人工数图认知到可复核的 Workflow

[返回项目首页](../README.md)

## 项目与我的角色

COOLBAO 面向消防报警图纸中的设备统计与点位表交付。项目探索如何把依赖人工识图和业务判断的工作，整理为软件可以执行、人员可以复核的流程。

我的工作覆盖前期 PoC 的需求拆解、流程设计与 AI 辅助原型推进，真实人工数图学习、设备配置与规则梳理，与 DXF 团队共同制定后续方案，以及已有能力整合与交接。同事负责既有网站与基础业务框架，AI 编码工具协助工程实现。

## 1. 问题：数出总数之前，需要先理解怎样数

人工数图同时包含图纸识读、设备识别、系统归属、楼层和标准层处理、配置判断、数量核对及表格填写。

一个图形对象未必直接等于一个最终计数单位；一个图名也未必足以说明全部适用楼层。即使合计接近人工表，也可能存在错归属或误识别与漏识别互相抵消。

因此，我在推进软件流程的同时深入学习技术人员的实际数图方式，重点梳理四个问题：

| 业务问题 | 对产品的影响 |
| --- | --- |
| 依据什么判断设备类别？ | 明确可采用的图块、属性、关联文字和业务确认依据 |
| 哪些图面和楼层纳入统计？ | 明确统计范围与标准层集合，保留歧义 |
| 特殊设备或配置怎样处理？ | 识别自动处理与人工判断的边界，避免无依据补齐 |
| 结果最终交给谁、以什么形式交付？ | 统一逐层数量、复核入口与两类表格的口径 |

## 2. 前期 PoC：先建立可检查的小闭环

我围绕图纸输入、结构化解析、报警七类试算、结果核对和逐层表格交付推进原型，借助 AI 编码工具缩短想法到可操作界面的距离。

首批范围收敛到感烟、感温、手报、消报、声光、扬声器和电话分机。这样可以围绕明确设备建立规则与样例，逐项判断原型表现和需要补充的业务依据。

PoC 的成果是形成前期可操作闭环、暴露流程和规则问题，并为后续讨论提供具体对象。原型流程完成与正式工程量验收是两项不同的工作。

## 3. 核心积累：将人工认知转化为产品要求

真实数图学习使我逐步能够从业务角度理解问题：需要先澄清设备、配置、范围和统计口径，再决定怎样修改产品。

| 学习与核对中遇到的问题 | 产品层面的处理 |
| --- | --- |
| 设备名称、符号或属性存在冲突 | 保留原值与冲突，结合原图及业务判断复核，限定裁决适用来源 |
| 标准层和多个子图共用图框 | 明确图名、图框、楼层集合及设备归属，疑点单列 |
| 扬声器安装形式无法确定 | 将安装形式保留为待确认，不自行填写模板的具体类型列 |
| 软件没有形成完整数量 | 明确展示未完成与原因，避免把未知理解为零设备 |
| 表格与技术人员交付习惯不一致 | 将逐层列示、楼栋组织、合计与零值呈现转成具体交付要求 |

这些处理既依赖技术实现，也依赖对人工工作方式的理解。我的产品工作是把问题问清楚、把适用范围写明确，并判断结果是否符合业务要求。

## 4. 关键取舍：简单流程与可复核结果同时保留

### 收敛用户主流程

普通使用者的任务是选择图纸、查看进度和结果、核对疑点、获取表格。我推动主流程围绕这些任务组织，减少获取结果前需要理解的内部概念。

### 明确系统与人的职责

结构信息与规则明确的部分交给软件试算；设备冲突、未知范围和特殊配置保留人工判断。来源、裁决依据和适用范围进入记录，支撑后续复核。

### 同一份数量支持两类交付

客户表与泰和安表基于同一统计版本导出。表格形式的变化不应引入第二套独立计数口径，缺少必要模板或安装形式时应明确说明。

### 与既有系统协同

在完成前期探索后，推动可复用能力接入同事的既有网站。围绕图框与楼层、对象追溯、复核与导出补强已有流程，并整理问题和接手材料。

## 5. 团队后续方案与个人阶段边界

我与 DXF 团队结合 PoC 和真实人工数图学习中发现的问题，共同制定后续方案。对设备配置、统计规则和人工判断方法的理解，为团队讨论下一阶段需求和验证方式提供业务依据。

**下一重点实施阶段尚未开展。** 本案例记录本人已经完成或参与的前期验证、规则认知建立、共同方案准备、能力整合与交接，不把后续计划写成已落地成果。

## 6. 如何判断产品是否有效

验证需要分别回答不同问题：

| 验证层次 | 需要回答的问题 |
| --- | --- |
| 软件流程 | 正常输入能否处理，失败是否可见，导出与保存来源是否一致？ |
| 业务结果 | 设备分类、范围、标准层和逐层数量是否符合冻结的人工核对口径？ |
| 交付表格 | 楼栋、楼层、公式和合计是否正确，表格能否在实际办公软件中使用？ |
| 使用收益 | 同一任务中，找点、计算、核对和整理表格分别花多少时间？ |

目前以流程变化展示收益。进一步评价节时比例或准确率，需要在相同输入、设备范围和交付要求下记录对照；软件测试项数与 GIF 时长不作为这些指标的替代。

## 7. 对 AI 产品工作的积累

这段实践让我学习怎样进入一个专业工作场景，通过人工操作、样例与疑点建立任务认知，再将认知转为产品流程、自动化边界和验证要求。

AI 工具帮助推进原型与工程协作；产品侧持续负责目标、范围、优先级、业务判断和结果核验。当前运行主链路采用 CAD 结构化解析与规则统计，案例不宣称实现了运行时多 Agent 自主规划。

可迁移的方法是：**理解真实任务 → 抽象规则 → 建立 PoC → 用样例验证 → 处理人机边界 → 与研发共同规划。**
